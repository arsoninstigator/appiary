# appiary architecture

## core mission

appiary is a middle saas layer that packages web apps generated by tools like lovable, base44, and replit into native ios and android apps. it automates configuration, previewing, and deployment without hosting physical mac infrastructure.

## step 0: source intake (three ways in)

appiary meets customers wherever their ai tool leaves them:

- **web url (wrap mode):** any published https url. known builder hosts are
  labeled for the dashboard (lovable, replit, base44, bolt.new, rocket.new,
  blink.new, zite.so, emergent, v0, rork, a0.dev, plus common static hosts
  like vercel, netlify, render, pages.dev). the url is injected into capacitor
  `server.url` and the app streams live in the webview. this covers users
  who cannot get their code out of the editor at all.
- **git repo (bundle mode):** github, gitlab, bitbucket, and gitea urls,
  including browse paths with refs (`/tree/<ref>`, `/-/tree/<ref>`,
  `/branch/<ref>`, `/src/branch/<ref>`). the runner clones, builds the web
  app (`npm ci && npm run build`), and stages the output into `www/`.
- **zip (bundle mode):** an uploaded artifact url; the runner unpacks and
  stages it the same way. workspace exporter tools feed this path directly:
  codejack, a sister app currently in development, is being built to download
  a user's entire ai-builder workspace as a zip or json. codejack gets the
  code out, appiary turns it into a native app. exporter zips usually wrap everything in one top-level
  folder, so `scripts/stage-source.js` flattens wrappers, picks the build
  output (dist / build / out / public), strips node_modules, and validates
  index.html before `npx cap sync`.

bundle mode ships the web assets *inside* the binary (no `server.url`), which
sidesteps capacitor's live-reload-only caveat and is the sturdier shape for
app review. code: `src/intake.js` (classify/normalize), `src/wrapper.js`
(`renderBundledConfig`), runner steps in the build workflow.

## step 1: client runtime wrapper

the hidden native template lives in `template/`: a self-contained capacitor
project (package.json pinned to capacitor 8.5.x, a `www/` placeholder page,
fastlane lanes, gemfile). platform folders (`ios/`, `android/`) are
deliberately not committed: each runner regenerates them with `npx cap add`
via `template/scripts/init-platforms.sh`, keeping the template small and
capacitor upgrades painless. the injected config already carries the user's
appId, so regenerated platforms come out branded to their bundle id.

- **wrap mode:** the web url goes into `server.url`; the webview streams the
  live app with native bridging enabled.
- **bundle mode:** the staged build lands in `www/` and ships inside the
  binary; no server.url at all.

### auth inside wrapped apps (origin realities)

the webview origin differs by mode, and oauth providers that pin redirect
uris to https care about this:

- **wrap mode:** the webview serves the user's https site directly, so the
  page origin is their real domain. sign-in flows, cookies, and redirects
  behave like a normal browser. this is the easy case.
- **bundle mode:** assets load from the device, so the origin is the
  capacitor scheme (`capacitor://localhost` on ios, `https://localhost` on
  android). https-only redirect uris will not match. the fixes are standard:
  run the flow in the system browser (the shell ships
  `@capacitor/browser`) and return through the app scheme, or use auth
  providers that document capacitor flows natively (supabase deep links,
  firebase custom schemes). supabase, insforge, and firebase all support
  this shape; the dashboard surfaces a per-app oauth callback hint once the
  appId is known.

users keep their own auth either way; appiary never proxies credentials.

### in-app purchases (premium add-on, after v1)

purchases cannot run in plain webview javascript: app store and play billing
are native-only apis. the path is the official revenuecat capacitor plugin
compiled into the shell with the user's public sdk keys (delivered through
the vault like every other credential), entitlements surfaced to the webview
through the plugin's js bridge, and receipts verified on the user's own
backend via revenuecat webhooks. scoped as a premium add-on: it touches the
template, the vault schema, and the workflow.

### offline apps

possible today, in bundle mode only: the web assets ship inside the binary,
so the app shell runs with no network at all. whether the app works offline
depends on its own code: static apps, tools, and games work as-is; apps
that call apis degrade the way they degrade in an offline browser. wrap mode
is online by definition (it streams the live site). advanced offline
storage can lean on standard web apis plus native sqlite later if customers
ask for it.

### device coverage

ios builds are universal: one binary covers iphone and ipad (capacitor's
xcode template ships with targeted device family 1,2, so the store lists
the app for both; ipados runs the same ios binary natively). watchos is not
covered. macos needs mac catalyst, a different build pipeline, parked with
the desktop rungs on the horizon (see docs/horizon.md).

## step 2: interactive browser preview

- **oss tool used:** appetize.io api (commercial) or simmer / tapflow (oss alternatives)
- **verified against current docs (docs.appetize.io/rest-api):** auth header is `x-api-key` (the old `x-appetize-dev` scheme is gone), create/update are `POST /v1/apps` and `POST /v1/apps/{publicKey}`, and `referrerHostnamesRestricted` can pin embedding to the appiary dashboard hostname. sessions start client-side from the iframe src, not via a rest endpoint.
- **how we use it:** to show an instant device preview on the appiary dashboard, our platform runs a quick headless debug build of the capacitor container. the resulting binary artifact is pushed via api to a simulator streaming service. our saas frontend embeds the resulting secure iframe, allowing the user to interact with their live app at 60fps inside their browser tab.
- **code:** `src/appetize.js`. `publishApp` uploads/replaces an app build (`.zip` for ios, `.apk` for android) and returns the `publicKey`; `embedUrlFor` builds the iframe src (`https://app.appetize.io/app/<publicKey>?device=...`). the transport is injectable, so simmer/tapflow adapters can implement the same surface.

## step 3: cloud compilation intermediary

- **oss tool used:** github actions api and hosted macos runners
- **how we use it:** instead of maintaining mac minis, appiary acts as an orchestrator. when a user clicks "deploy," our backend triggers a repository dispatch event to the github actions api. we pass the app configuration, app metadata, icons, and encrypted credentials as secure json payloads. an ephemeral github macos runner spins up on-demand to execute the heavy-duty native compilation.
- **code:** `src/github.js` (dispatch + run status), `.github/workflows/appiary-build.yml` (runner side). the payload carries only the rendered capacitor config, metadata, the single-use handoff token, and a callback url. **no secrets travel inside the dispatch payload.**

## step 4: automated signing and submission

- **oss tool used:** fastlane (current 2.241.x), verified against docs.fastlane.tools. one correction from the docs: `deliver` is an alias of `upload_to_app_store` and is ios-only - the play console upload is `supply` (alias `upload_to_play_store`) with `aab`, `json_key`, `track`. also note fastlane/fastlane#14686: the very first play upload for a new app must be done manually before supply can automate updates.
- **how we use it:** inside the github action runner, a fastlane script is executed. fastlane consumes the user's apple developer api keys (`.p8` files) redeemed from the handoff endpoint. it executes `fastlane match` to handle provisioning profiles headlessly, `fastlane gym` to build the production `.ipa` / `.aab` binary, and `fastlane deliver` to push the completed build directly to apple testflight or the google play console.
- **code:** `template/fastlane/Fastfile` with `ios release`, `ios preview` (debug artifact for step 2), and `android release` lanes. match runs `readonly: true`; keychain is deleted in the runner cleanup step.

## pipeline state machine

```
received -> wrapped -> previewing -> dispatched -> building -> submitted -> done
                                                   \-> failed
```

`src/pipeline.js` journals every transition into the job record so the dashboard can render live state and jobs can be inspected after completion. status callbacks from the runner (`POST /report`) drive the tail states.

## what is deliberately not in this repo yet

- the dashboard ui (embeds the appetize iframe, shows job states)
- the xcode / android studio project files inside the hidden template (generated once by `npx cap add ios/android`, then committed)
- icon/splash generation from the web app's assets
- billing and quota

see `docs/credential-flow.md` for the security protocol, and
`docs/cost-model.md` for the provider pricing decisions (preview streaming via
vibeview, mac build runners via bitrise build hub, both switchable without
touching the pipeline because the runner label and preview provider are
per-dispatch / adapter-level choices).
