# appiary architecture

## core mission

appiary is a middle saas layer that packages web apps generated by tools like lovable, base44, and replit into native ios and android apps. it automates configuration, previewing, and deployment without hosting physical mac infrastructure.

## step 1: client runtime wrapper

- **oss tool used:** capacitor (by ionic), verified against the v8 config schema (current stable 8.5.3; v9 is alpha). note: capacitor documents `server.url` as a live-reload option, "not intended for use in production" - the wrapper emits this warning on every render so store-review risk is explicit.
- **how we use it:** we maintain an internal, hidden native project template built with capacitor. when a user inputs a lovable web url, our backend injects this url into the capacitor configuration file (`capacitor.config.json`) under the `server.url` property. this wraps the web app instantly inside a native webview container with native bridging enabled.
- **code:** `src/wrapper.js` renders `template/capacitor.config.template.json`. validation rejects non-http(s) urls, urls with embedded credentials, and plain-http targets unless the caller explicitly opts into cleartext (and gets a store-review warning).

## step 2: interactive browser preview

- **oss tool used:** appetize.io api (commercial) or simmer / tapflow (oss alternatives)
- **verified against current docs (docs.appetize.io/rest-api):** auth header is `x-api-key` (the old `x-appetize-dev` scheme is gone), create/update are `POST /v1/apps` and `POST /v1/apps/{publicKey}`, and `referrerHostnamesRestricted` can pin embedding to the appiary dashboard hostname. sessions start client-side from the iframe src, not via a rest endpoint.
- **how we use it:** to show an instant device preview on the appiary dashboard, our platform runs a quick headless debug build of the capacitor container. the resulting binary artifact is pushed via api to a simulator streaming service. our saas frontend embeds the resulting secure iframe, allowing the user to interact with their live app at 60fps inside their browser tab.
- **code:** `src/appetize.js`. `publishApp` uploads/replaces an app build (`.zip` for ios, `.apk` for android) and returns the `publicKey`; `embedUrlFor` builds the iframe src (`https://app.appetize.io/app/<publicKey>?device=...`). the transport is injectable, so simmer/tapflow adapters can implement the same surface.

## step 3: cloud compilation intermediary

- **oss tool used:** github actions api and hosted macos runners
- **how we use it:** instead of maintaining mac minis, appiary acts as an orchestrator. when a user clicks "deploy," our backend triggers a repository dispatch event to the github actions api. we pass the app configuration, app metadata, icons, and encrypted credentials as secure json payloads. an ephemeral github macos runner spins up on-demand to execute the heavy-duty native compilation.
- **code:** `src/github.js` (dispatch + run status), `.github/workflows/appiary-build.yml` (runner side). the payload carries only the rendered capacitor config, metadata, the single-use handoff token, and a callback url. **no secrets travel inside the dispatch payload.**

## step 4: automated signing and submission

- **oss tool used:** fastlane (current 2.241.x), verified against docs.fastlane.tools. one correction from the docs: `deliver` is an alias of `upload_to_app_store` and is ios-only - the play console upload is `supply` (alias `upload_to_play_store`) with `aab`, `json_key`, `track`. also note fastlane/fastlane#14686: the very first play upload for a new app must be done manually before supply can automate updates.
- **how we use it:** inside the github action runner, a fastlane script is executed. fastlane consumes the user's apple developer api keys (`.p8` files) redeemed from the handoff endpoint. it executes `fastlane match` to handle provisioning profiles headlessly, `fastlane gym` to build the production `.ipa` / `.aab` binary, and `fastlane deliver` to push the completed build directly to apple testflight or the google play console.
- **code:** `template/fastlane/Fastfile` with `ios release`, `ios preview` (debug artifact for step 2), and `android release` lanes. match runs `readonly: true`; keychain is deleted in the runner cleanup step.

## pipeline state machine

```
received -> wrapped -> previewing -> dispatched -> building -> submitted -> done
                                                   \-> failed
```

`src/pipeline.js` journals every transition into the job record so the dashboard can render live state and jobs can be inspected after completion. status callbacks from the runner (`POST /report`) drive the tail states.

## what is deliberately not in this repo yet

- the dashboard ui (embeds the appetize iframe, shows job states)
- the xcode / android studio project files inside the hidden template (generated once by `npx cap add ios/android`, then committed)
- icon/splash generation from the web app's assets
- billing and quota

see `docs/credential-flow.md` for the security protocol, and
`docs/cost-model.md` for the provider pricing decisions (preview streaming via
vibeview, mac build runners via bitrise build hub, both switchable without
touching the pipeline because the runner label and preview provider are
per-dispatch / adapter-level choices).
